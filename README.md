# 穹幕投影机校准 · 精确路线台

穹幕投影机校准时需要把**全部姿态（1…N）各测量一次**，镜组在姿态之间转动的耗时
**有方向性**（`C[i→j] ≠ C[j→i]`，非对称）。凭经验排序会浪费宝贵的停机窗口。

本工具给出：

1. **编辑与导入台**：维护 `(N+1)×(N+1)` 的非对称费用矩阵与**可选的“先于”关系**（如基准姿态
   必须先于依赖它的姿态），严格校验，坏数据整批拒绝、旧计划保留；
2. **校准路线候选集（精确解区域）**：从停放位 `0` 出发，每个姿态恰好访问一次并回到 `0`，
   且只在某姿态的**全部先于姿态都已访问**时才扩展状态；计划应用后**一次给出按总耗时升序、
   同费按完整姿态序列字典序升序排列的前三条互异精确路线**，逐条显示排名、总耗时与从 `0`
   出发回到 `0` 的完整路径；**默认选择首名**，工程师可改选后进入执行台。可行路线不足三条时
   只返回实际数量（无占位、无重复）；约束使一条可行路线都没有时不产出候选（提交时已保证无环，
   此为防御分支）；
3. **现场执行台**：以**所选候选**为原计划及增量基线；工程师可把**任一前置姿态均已确认的
   未完成姿态**确认为实际下一站（随时偏离所选路线），**前置未满足的确认会被拒绝且已确认进度
   原样保留**；页面累加已发生费用，并**以该姿态为新起点、只在剩余姿态上（继续遵守依赖，
   已完成姿态视为满足）精确重排**，给出最短收尾路线、预计完工耗时及相对**所选候选**的增量
   （基线为次优候选时增量允许为负）；已完成姿态立即禁用，不能再次确认。

> 求解器是 **Held–Karp 动态规划**，精确最优——**不是贪心，也不是全排列枚举**。
> 所有计算都在浏览器本地完成；**数据只留在浏览器**（`localStorage`），没有任何后端 API。

## 适用范围与硬性规则

| 项目 | 规则 |
| --- | --- |
| 姿态编号 | `1…N`，`N` 取 **8—18** 的整数；`0` 为停放位 |
| 费用矩阵 | `(N+1) × (N+1)` 方阵，行优先二维数组，`matrix[i][j]` = 从 `i` 转到 `j` 的耗时 |
| 主对角线 | **必须为 0**（编辑器中锁定，不可改） |
| 非对角项 | **1—9999 的整数**（有方向性，不要求对称；小数、负数、缺项等一律拒绝） |
| 整批拒绝 | 任一缺项、越界、形状不符、类型错误 → **整批拒绝并保留旧计划**，错误就地显示 |
| 目标 | 从 `0` 出发，每个姿态恰一次，回到 `0`，总耗时最小 |
| 先于关系 | 可选 `precedences`（别名 `before`）：`[a, b]` 表示姿态 `a` 必须先于姿态 `b`；只在 1…N 之间、**不可自指**、**依赖图必须无环**，重复关系去重；违反任一条整批拒绝 |
| 候选 | 计划应用后一次给出**前 3 条互异且满足全部先于关系的精确路线**，按总耗时升序、同费按完整姿态序列字典序升序；不足 3 条只返回实际数量 |
| 执行 | 确认下一站前再次检查先于前置，**未满足则拒绝且保留已确认进度**；中途重算只在剩余姿态上继续遵守依赖，已完成姿态视为满足 |
| 并列 | 路线费用相同时，按姿态序列**字典序**排序，首名即满足约束的字典序最小最优解 |
| 性能 | **N=18 生成三条候选 < 4 秒**（本机实测约 0.7—1.3 s；现场每拍单最优重排随剩余数递减，更快） |

支持的 JSON 形态（含数字与数组，工程师可手工编辑或导入）：

```json
{
  "n": 8,
  "matrix": [
    [0, 12, 7, 33],
    [9, 0, 41, 5],
    [7, 38, 0, 11],
    [30, 6, 14, 0]
  ],
  "precedences": [[1, 3], [2, 3]]
}
```

上例表示姿态 `1`、`2` 都必须先于姿态 `3` 完成。也可在编辑台的**“先于”关系草稿**面板里
按行书写（`1, 3` / `1 -> 3` / `1→3` / “1 先于 3”均可，`#` 开头为注释）。

- `matrix` 也可写成 `costs`；`precedences` 也可写成 `before`；
- 也接受**裸二维数组**，此时 `N = 边长 - 1`，且没有“先于”关系；
- 没有 `precedences` 字段的旧输入一律按无依赖处理，结果与旧版本逐项一致；
- 文件导入（`.json`）与文本框粘贴等价，先入草稿，**校验通过后点“校验并应用”才生效**；
  关系草稿与已应用计划分离，非法依赖（姿态不存在、自指、有环/相互约束）整批拒绝，
  上次有效计划与候选路线不会被污染。

## 算法说明（为什么是精确解，且一次给出前三名）

定义（`src/solver/tsp.ts`），每个状态不再只存单个最优值，而是固定保留 `k=3` 名**不同后缀**
及其子排名：

```
g[mask][i][r] = 从 target[i] 出发，恰好访问 mask 中全部目标（i 不在 mask 内），最后回到 0
               的全部互异后缀中，第 r 名（按总耗时升序、同费按后缀字典序升序）的耗时
g[0][i][0]    = C(target[i] → 0)
g[mask][i]    = 对每个 j ∈ mask 合并候选流
                 C(target[i] → target[j]) + g[mask \\ {j}][j][*]，取前三名
```

答案：对首个姿态 `i` 合并 `C(0 → target[i]) + g[full \\ {i}][i][*]`，取前三名。

**可选“先于”关系（`src/solver/precedence.ts`）**：关系 `a 先于 b` 编译成 `b` 的前置位掩码
（位 `a` 置位），求解前投影到当前目标子集得局部掩码 `preMask[j]`——子集外的前置（执行中途
即“已完成姿态”）自动剔除，视为已满足。DP 扩展与顶层首选都只接受
`(待访集合 & preMask[j]) == 0` 的后继 `j`，即**只在前置姿态已访问时扩展状态**；被门控掉的
后继不产生候选流，前三名合并、k 最优引理与字典序 tie-break 均不变。无该参数时掩码恒为 0，
求解路径与旧版本完全一致。可行路线（剩余依赖图的拓扑序）少于 3 条时只返回实际数量；提交时
的无环校验保证完整图总有拓扑序，求解器对“零可行”仍防御性返回空候选集 / 抛错。

- 每个后继 `j` 给出一条已按 `（耗时, 后缀字典序）` 排好序的候选流；不同 `j` 的首姿态不同，
  同一 `j` 的不同子排名对应互异后缀，所以 `(j, 子排名)` 一一对应互异完整序列，**无需去重**，
  也**不靠禁用首选路线中的边反复调用求解器**。
- k 最优引理：父状态的第 `k` 名必来自某条候选流的前 `k` 名，故子状态只存三名即足够。
- **同费字典序 tie-break**：目标按编号升序；同费候选之间首姿态编号小者整序列更小，合并键
  直接取 `（耗时, j, 子排名）`，恢复时沿 `(后继位, 子排名)` 指针确定性回溯，无需保存序列。
- 紧凑存储：耗时 `Int32Array`（每状态 3 槽，无效槽为哨兵），`(后继位, 子排名)` 打包成
  `j*3+r` 存 `Int8Array`（`j ≤ 19`，单字节足够）。
- 时间复杂度 `O(k·m²·2^m)`，空间 `O(k·m·2^m)`；m=18、k=3 约 1400 万个耗时槽，亚秒至一秒级。
- 互异路线总数 `m!` 不足 3 时（小目标数/剩余子集），答案只有实际数量，**无占位、无重复**。
- `solveOptimal` 走同一 DP 核心的 `k=1` 快路径，**恒等于候选首名**，继续服务既有现场
  后缀重排；**现场重排**只是把 `origin` 从 `0` 换成刚确认的姿态、目标集合换成剩余姿态再解一次
  （先于掩码按剩余子集投影，已完成姿态视为满足）；每一拍得到的后缀都是该状态下满足约束的
  全局最优后缀。确认时状态机用同一掩码再查一次前置，未满足即拒绝、不产生新状态。
- 预计完工 = 已发生费用 + 当前精确最短后缀（含返回 `0` 的边）；增量 = 预计完工
  − **所选候选基线**。基线是候选首名（精确最优）时增量恒 `≥ 0`；工程师改选次优候选后，
  初始精确最短后缀严格更短，**增量允许为负**。
- **应用新矩阵时旧候选与工程师的选择一起失效**：候选集对已生效计划引用做记忆化，
  计划替换即重算并把选择重置为首名。

产品代码中**没有**贪心近似，也**没有** `m!` 枚举；全排列枚举只存在于测试基准
（`src/solver/brute.ts` 的 `bruteForceTopK`），用于穷举小样本核对前三名、数量不足与互异性。

```bash
npm install

npm run build      # 类型检查 + 生产构建到 dist/
npm run preview    # 预览生产构建
```

## Docker Compose

多阶段 `Dockerfile`：

- `web` 阶段：构建静态产物并用 **nginx** 发布（纯静态，无后端）；
- `verify` 阶段：装依赖后执行 `npm run verify`，**一次性**，退出码即验收结论。

### 发布页面（端口可用 `WEB_PORT` 覆盖）

```bash
# 默认 8080
docker compose up -d --build web
# 打开 http://localhost:8080

# 覆盖端口
WEB_PORT=9000 docker compose up -d --build web
# 或复制 .env.example 为 .env 后修改 WEB_PORT
```

### 一次性验收

```bash
docker compose --profile verify run --rm verify
```

`verify` 挂在 `verify` profile 下，不会随 `docker compose up` 启动，也不会被重启；
跑完穷举核对与 N=18 性能指标后容器退出。

## 数据与隐私

- 已生效计划（矩阵 + 已应用的“先于”关系）只写入当前浏览器的 `localStorage`（键
  `dome-calibration-plan-v1`），加载时重新校验，损坏数据自动回退默认计划；没有关系时
  不写该字段，旧版本存下的数据可直接读取。
- 应用本身不发起任何网络请求（无 `fetch` / XHR / WebSocket / 埋点）；
  部署形态是 nginx 静态文件。清空站点数据或点击“恢复默认计划”即可删除本地数据。

## 项目结构

```
src/
  solver/
    plan.ts        # 数据模型 + 严格整批校验（矩阵 + 可选“先于”关系）

                   #   可选前置掩码：只在前置已访问时扩展状态）
    execution.ts   # 执行状态机：开始（所选候选为基线）/ 前置检查后确认下一站并精确重排 / 回库（纯函数）
    brute.ts       # 仅测试用：全排列穷举基准（最优 + 前三名，支持先于约束）+ 可复现随机矩阵/无环关系
    *.test.ts      # 前三名穷举核对、先于约束独立枚举、环与相互约束、逐步偏离与负增量验收、N=18 性能
  components/
    MatrixEditor.tsx     # N 选择、逐格编辑、“先于”关系草稿、JSON 导入/导出、就地错误
    CandidatePicker.tsx  # 校准路线候选集：前三名满足依赖的互异路线、默认首名、可改选
    ExecutionConsole.tsx # 指标卡、路线、姿态确认（阻塞拦截）、回库、最终台账
    RouteLine.tsx        # 路线（节点 + 逐边费用）渲染
    components.test.tsx  # UI 行为测试（含临时改依赖、执行拒绝、重算同步）
  state/storage.ts       # localStorage 读写（再校验后才落盘；无关系时旧载荷形状不变）
  App.tsx                # 编辑台 / 执行台页签（应用新矩阵即重算候选并重置选择）
Dockerfile  docker-compose.yml  nginx.conf  .env.example
```
